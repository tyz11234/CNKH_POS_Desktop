## Test scheduling

- **Image completion predicate can be early.** Mobile `test/product_image_edit_regression_test.dart:53` now alternates real I/O and pumping with a 10-second deadline, which removes its previous fixed 100 ms assumption. Its predicate at lines 64–65 is only `directory.list().length == expected`. Desktop `test/product_image_editor_safety_test.dart:103` similarly returns when a second file appears. In both product editors, `imagePath = saved` happens only after awaited `saveFromFile` / file copying returns. A filesystem entry can be visible before copying and the picker callback's UI update finish. An early Save tap could therefore test a pending picker rather than a selected replacement. This is a possible race, not a reproduced failure. A stronger fixture would wait for the dialog's `Image.file` to reference the new file and verify its expected bytes before Save, keeping the original preservation assertions. These filesystem reads have no SQLite transaction dependency, so they do not reproduce Round 1's supplier-query deadlock.
- **Purchase dialog settle can precede its bounded wait.** Desktop `admin_dialog_controller_lifecycle_test.dart:87` calls `pumpAndSettle` immediately after closing a focused Save dialog. `PurchaseDetailPage` sets `_editing = true`, awaits the real metadata transaction and reload, and shows a continuously animated `CircularProgressIndicator` while `_editing` is true (`purchase_detail_page.dart:233`, `:544`). The later test wait for the success snackbar is correctly bounded and precedes the database assertion, but a slow Windows I/O response can make the earlier global settle time out before that helper is reached. Consider pumping the route transition, then using the existing real-I/O/observable completion wait before settling. No such timeout was observed in this read-only subtask.
- **Scanner and mock-only lifecycle tests are deterministic at the inspected boundary.** Mobile scanner acceptance and Desktop scanner feedback repositories override product lookup/settings with immediately completing futures; their delayed acceptance `Completer<bool>` is explicitly completed before the final pump. Desktop platform feedback is mocked. Neither uses SQLite or a real camera for these assertions. Mobile product dialog and Desktop cart discount lifecycle repositories likewise provide immediate mocks, so no pending FFI lock is present.
- **Real purchase fixture observes commit completion before querying.** Mobile `purchase_amount_boundary_regression_test.dart` now sets `purchaseCompleted` after `super.createPurchase` returns and pumps real I/O until that flag for its successful-save scenario. Its subsequent purchase/stock reads therefore occur after the real transaction. Initial UI bootstrap still uses fixed flushes, so watch for missing controls on an unusually slow runner; no failure is established.

The failed fixture ends each test with the product page still mounted, then immediately deletes its temporary directory. Both product pages and dialogs render `Image.file`. Flutter 3.47.6 `FileImage._loadAsync` uses asynchronous `ui.ImmutableBuffer.fromFilePath`, so pending engine reads/decodes can retain native file handles after a virtual `pumpAndSettle` and block Windows recursive deletion. The stack proves the deletion stage; it does not identify which exact handle/process held the file.

Advice sent to the Desktop fixture owner: explicitly unmount the image widgets, pump, alternate real I/O and frames until pending image decode work finishes with a bounded, asserted condition; then evict/clear image cache/live images before deleting fixture files. Check pending work **before** clearing the cache, since clearing resets cache counters and is not proof that native work completed. Preserve deletion failures if cleanup still cannot finish; do not skip, swallow OS32 or merely retry deletion while hiding active handles.

Mobile's new product-image fixture also has direct recursive directory deletion in `addTearDown`, while its page/dialog render `Image.file`; it therefore shares the cleanup risk.
